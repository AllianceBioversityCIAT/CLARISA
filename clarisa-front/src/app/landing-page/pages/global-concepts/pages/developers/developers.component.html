Persistent URIs and content negotiation

Every concept has a permanent address, its term_uri. Cite it instead of a page link: it never changes, even when the concept is deprecated. A browser opening it is sent to the human page; a program asking for data gets data.

  • Accept: text/turtle → SKOS in Turtle
  • Accept: application/ld+json → JSON-LD
  • Accept: application/json → the JSON record
  • Or force it with ?format=skos|jsonld|json when you cannot set headers.

The whole scheme answers the same way at {{ bases.uris }}/{{ scheme }}. Always read the URI from term_uri: its domain is set per environment.

Exports

The whole scheme in one file, in four formats. The same buttons are on the list page under "Download".

  • JSON — every public field, the same shape as the API.
  • CSV — opens in Excel with the columns of the MELIAF template, plus one column per public custom field.
  • SKOS Turtle and JSON-LD — linked data for vocabulary tools and the web.

Change feed and version pinning

To keep a local copy up to date, do not download everything every night: read the change feed. Each change has a growing cursor; ask for what happened after the last one you saw, then fetch only the concepts it names.

To make a report reproducible, pin a release: add ?version= to a concept, a search or an export and the answer is the vocabulary as it was published in that release. The list of releases is at /{{ scheme }}/releases.

Get counted: send your CLARISA API key

Reads stay open without a key. If your platform already has a CLARISA API key, send it in the X-API-Key header on every read (API endpoints, persistent URIs and MCP): the answer is exactly the same, and the MELIAF team can see which connected systems use the vocabulary, not only the search portal.

  • Any active key counts; no scope is needed to read.
  • A key that is unknown, revoked or expired never blocks the read. The answer then carries X-Api-Key-Status: invalid, so you can notice and ask for a new key.
  • Send it from your server, never from a public web page: whoever sees the key can use it.

Platforms and API keys

Reading needs nothing. A platform (PRMS, a MIS, a reporting tool) that wants to propose concepts on behalf of its users, or manage a scheme of its own, uses an API key issued by the CLARISA team. The key goes in the x-api-key header and carries one or more scopes:

  • concepts:read — reserved for keyed reading. Today every public read works without a key, so no route asks for it yet (any valid key is counted, with or without it).
  • concepts:request — submit requests and follow them. The stewards still decide; nothing is published by the key.
  • concepts:write — create and edit concepts directly, only in the scheme the platform owns.
  • concepts:review — decide requests, only in the scheme the platform owns.

The shared MELIAF scheme can never be written by a key: platforms propose, the MELIAF stewards approve.

AI assistants (MCP)

MCP (Model Context Protocol) is a common way to plug a source of information into an AI assistant such as Claude or ChatGPT. Once you add the address below, the assistant can look up the official CGIAR concepts by itself while it answers you, and quote the definitions and their links instead of making them up. It only reads what is already public here; it cannot change anything.
